# 로그인·계정 연동 설계

레오파드 모프 계산기의 인증 설계 문서입니다. 소셜 로그인을 추가하거나 계정 관련 코드를 고칠 때
**먼저 이 문서를 읽고**, 바꾼 내용을 여기에도 반영해 주세요.

- 최초 작성 2026-07-27
- 대상 provider: 이메일+비밀번호(구현됨), Google(구현됨), Kakao(예정), Apple(iOS 출시 시 필수)
- 백엔드: Supabase Auth

> **문서 상태 표기**
> `[구현]` 코드에 반영됨 · `[설계]` 결정됐으나 미구현 · `[확인필요]` 사실 확인이 끝나지 않음

---

## 1. 무엇을 풀어야 하는가

소셜 로그인을 여러 개 붙이면 "한 사람 = 한 계정"을 유지하기가 어려워집니다. 문제는 네 갈래입니다.

1. **중복 계정** — 같은 사람이 구글로도, 카카오로도, 이메일로도 가입해 계정이 셋으로 쪼개짐
2. **계정 탈취** — 이메일만 같으면 자동으로 합쳐 주는 순진한 구현은 남의 계정을 뺏는 통로가 됨
3. **이메일 없는 가입** — 카카오는 이메일이 선택 동의라 이메일을 아예 못 받을 수 있음
4. **로그인 수단 상실** — 마지막 남은 로그인 수단을 해제하면 본인도 못 들어옴

여기에 **Apple App Store 심사 지침 4.8**이 겹칩니다. iOS 앱에서 구글·카카오 로그인을 제공하면
동등한 대체 로그인 수단을 같이 제공해야 합니다.

---

## 2. 위협 모델 — 이메일 자동 연동은 왜 위험한가

가장 중요한 부분입니다. **"이메일이 같으면 같은 사람"이라는 가정은 성립하지 않습니다.**

### 2.1 선점형 계정 탈취 (account pre-hijacking)

공격자가 **피해자보다 먼저** 피해자의 이메일로 계정을 만들어 두는 방식입니다.

```
1. 공격자가 victim@gmail.com 으로 이메일+비밀번호 가입 (메일 인증은 안 함)
2. 시간이 지나 진짜 주인이 구글 로그인으로 victim@gmail.com 접속
3. 시스템이 "이메일 같네" 하고 자동 연동
4. → 공격자가 예전에 설정한 비밀번호가 여전히 살아 있음
5. → 공격자가 피해자 계정에 그대로 로그인 가능
```

피해자는 정상적으로 자기 구글 계정으로 로그인했을 뿐이라 **이상을 눈치채지 못합니다.**

### 2.2 미검증 이메일을 주는 provider

일부 provider는 사용자가 입력한 이메일을 검증 없이 그대로 넘겨줍니다.
공격자가 자기 소셜 계정의 이메일을 `victim@gmail.com`으로 바꿔 두면, 자동 연동 시 그대로 남의 계정에 들어갑니다.

### 2.3 결론 — 연동 규칙

> **이메일은 "같은 사람인 것 같다"는 힌트일 뿐, 증명이 아니다.**
> 연동은 반드시 **양쪽 모두 검증된 이메일**이거나, **기존 계정에 대한 소유 증명**이 있을 때만 한다.

## 3. 로그인 시 판정 규칙 `[설계]`

소셜 로그인 콜백이 돌아왔을 때 아래 순서로 판정합니다.

| # | 상황 | 처리 |
|---|---|---|
| 1 | 이 provider UID가 이미 연결돼 있음 | 그냥 로그인 |
| 2 | provider가 이메일을 안 줌 | **이메일 수집 화면** → OTP 인증 → 3번으로 |
| 3 | provider 이메일이 **미검증** | 자동 연동 금지. OTP로 직접 인증받고 4번으로 |
| 4 | 검증된 이메일, 같은 이메일 계정 **없음** | 새 계정 생성 |
| 5 | 검증된 이메일, 같은 이메일 계정 **있음** + 그 계정 이메일도 검증됨 | **연동 확인 화면** → 소유 증명 → 연동 |
| 6 | 검증된 이메일, 같은 이메일 계정 있음 + 그 계정 이메일이 **미검증** | **연동 금지.** 기존 계정 인증 먼저 요구 |

### 3.1 "소유 증명"으로 인정하는 것

5번에서 요구하는 증명입니다. 아래 중 **하나**를 통과해야 연동합니다.

- 기존 계정의 **비밀번호 입력** (비밀번호가 설정된 계정인 경우)
- 기존 계정 이메일로 보낸 **일회용 코드(OTP) 입력**
- 이미 연결된 **다른 소셜 로그인**으로 로그인

증명 없이는 절대 합치지 않습니다. 증명을 못 하면 "이미 가입된 이메일입니다.
기존 방법으로 로그인해 주세요"로 안내하고 **새 계정을 만들지도 않습니다.**
(새 계정을 만들어 주면 중복 계정이 늘고, 사용자는 자기 데이터가 사라진 줄 압니다.)

### 3.2 자동 연동은 언제 허용하나

**6번 케이스를 막기 위해 Supabase의 자동 연동 설정은 끄는 것을 기본으로 합니다.** `[확인필요]`
Supabase가 같은 이메일에 대해 어떤 기본 동작을 하는지, 설정으로 끌 수 있는지 확인 후 확정합니다.

## 4. 이메일을 못 받는 경우 `[설계]`

카카오는 이메일이 **선택 동의** 항목입니다. 사용자가 거부하면 이메일 없이 인증이 끝납니다.
전화번호로만 만든 카카오 계정은 이메일 자체가 없을 수도 있습니다. `[확인필요]`

### 처리 원칙

1. **가입을 완료시키지 않습니다.** 이메일 없이 계정을 만들면 나중에 계정 복구·중복 판정·공지 발송이 전부 막힙니다.
2. 인증 직후 **이메일 입력 화면**을 띄웁니다. ("계정 보호를 위해 이메일이 필요해요")
3. 입력받은 이메일로 **OTP를 보내 검증**합니다. 사용자가 타이핑한 이메일은 그 자체로는 신뢰하지 않습니다.
4. 검증이 끝나면 3장의 판정 규칙 4번/5번으로 들어갑니다.
5. 이메일 입력을 거부하면 가입을 취소하고, 왜 필요한지 안내합니다.

> **왜 이렇게까지 하나** — 사용자가 남의 이메일을 입력할 수 있기 때문입니다.
> OTP 검증 없이 그 이메일로 기존 계정을 찾아 연동하면 2장의 공격이 그대로 재현됩니다.

---

## 5. 로그인 수단 관리 `[설계]`

### 5.1 마지막 수단 해제 금지

**해제 후에도 "사용 가능한 로그인 수단"이 1개 이상 남아야 합니다.**

"사용 가능"의 정의가 중요합니다. 단순히 identity 개수를 세면 안 됩니다.

- 이메일 identity가 있어도 **비밀번호가 설정돼 있지 않으면** 로그인 수단이 아닙니다
  (구글로만 가입한 계정은 이메일 identity가 있어도 비밀번호가 없습니다)
- 따라서 판정은 `소셜 identity 개수 + (비밀번호 설정됨 ? 1 : 0) >= 2` 일 때만 해제 허용

해제하려는 것이 마지막 수단이면 버튼을 비활성화하고 이유를 보여 줍니다.
"이 계정의 유일한 로그인 방법이에요. 다른 방법을 먼저 추가해 주세요."

### 5.2 연동·해제는 민감 작업

- 연동/해제 전에 **재인증**을 요구합니다 (최근 로그인 시각이 오래됐으면 다시 로그인)
- 새 로그인 수단이 추가되면 **기존 이메일로 알림을 보냅니다.**
  탈취당했을 때 본인이 가장 빨리 알아챌 수 있는 신호입니다.

## 6. 탈퇴 시 처리 `[일부 구현]`

현재 `delete_my_account()`는 DB 데이터와 `auth.users`만 지웁니다.
**소셜 provider 쪽 연결은 정리하지 않고 있습니다.** 이건 고쳐야 합니다.

### 6.1 provider별로 해야 할 일

| Provider | 필요한 처리 | 안 하면 생기는 문제 | 상태 |
|---|---|---|---|
| Kakao | 연결 끊기(unlink) API 호출 | 카카오 계정에 앱이 계속 연결된 채로 남음 | `[설계]` |
| Apple | 토큰 폐기(revoke) API 호출 | **App Store 심사 거부 사유** | `[설계]` |
| Google | 토큰 폐기 (권장) | 동의 화면에 앱이 남음 | `[설계]` |

정확한 API 스펙은 조사 결과 반영 후 확정합니다. `[확인필요]`

### 6.2 순서

provider 연결 해제를 **DB 삭제보다 먼저** 시도합니다.
DB를 먼저 지우면 provider 토큰을 잃어버려 연결 해제를 영영 못 합니다.

```
1. 각 provider 연결 해제 시도 (실패해도 기록만 남기고 진행)
2. 개체·페어링·클러치·사진 삭제
3. 동의 기록 익명화 보관 (법정 5년)
4. 프로필 삭제
5. auth.users 삭제
```

연결 해제에 실패한 provider는 별도 테이블에 남겨 두고 재시도할 수 있게 합니다.
(사용자를 붙잡아 둘 수는 없으므로 탈퇴 자체는 진행합니다.)

## 8. 현재 코드의 상태

### 구현된 것
- 이메일+비밀번호 가입/로그인/재설정
- Google OAuth 로그인
- 약관 동의 게이트 (`renderConsentGate`) — 소셜 가입자도 동의를 받음
- 회원탈퇴 (`delete_my_account`) — DB 정리까지만

### 없는 것 (이 문서가 다루는 범위)
- 계정 연동/해제 UI 자체가 **전혀 없음** (`linkIdentity`/`unlinkIdentity` 미사용)
- 중복 이메일 판정 로직 없음
- 이메일 미제공 대응 없음
- 마지막 로그인 수단 보호 없음
- 탈퇴 시 provider 연결 정리 없음
- Kakao, Apple provider 미연동

## 9. 빠뜨리기 쉬운 것들

설계·구현 시 함께 챙겨야 하는 항목입니다.

### 인증 관련
- **Apple은 최초 1회만 이름·이메일을 준다** — 첫 콜백에서 저장 안 하면 영영 못 받음 `[확인필요]`
- **Apple Private Relay 이메일** — `@privaterelay.appleid.com` 형태. 이메일 기준 중복 판정이 무의미해지고,
  사용자가 전달을 끊으면 메일이 반송됨 `[확인필요]`
- **소셜 쪽 이메일이 바뀌는 경우** — provider UID를 기준으로 삼고 이메일은 참고값으로만 씀
- **provider 장애** — 카카오 점검 중이면 로그인 불가. 다른 수단 안내 문구 필요
- **로그아웃 범위** — 카카오는 "앱 로그아웃"과 "카카오계정 로그아웃"이 다름. 공용 PC 고려

### 계정 병합 시
- **두 계정에 각각 데이터가 있으면?** — 개체·페어링·클러치를 어느 쪽으로 합칠지 정책 필요.
  현재 `claim_device`는 기기→계정 이관만 처리하고 계정↔계정 병합은 없음
- **프리미엄 코드 승계** — 양쪽에 코드가 있으면 만료일이 더 긴 쪽을 살릴지 등
- **병합은 되돌릴 수 없음** — 실행 전 확인 화면 필요

### 법적·정책
- **소셜 가입자도 만 14세 이상 확인**이 필요 (현재 동의 게이트가 처리 중)
- **개인정보처리방침에 provider별 수집 항목 명시** — 카카오·애플 추가 시 방침도 같이 고쳐야 함
- **카카오 비즈앱 전환** — 이메일 수집 동의항목을 쓰려면 필요할 수 있음 `[확인필요]`
- **탈퇴 후 재가입** — 같은 소셜 계정으로 다시 가입해도 이전 데이터는 없음을 명확히 안내
  (현재 탈퇴 화면에 이미 문구 있음)

## 10. 구현 순서 제안

1. 계정 화면에 **연결된 로그인 수단 목록** 표시 (읽기 전용) — 현황 파악부터
2. **마지막 수단 보호** 로직 + 해제 UI
3. **연동 UI** (증명 절차 포함)
4. **탈퇴 시 provider 연결 해제**
5. Kakao provider 추가 (이메일 미제공 대응 포함)
6. Apple provider 추가 (iOS 출시 시점)
