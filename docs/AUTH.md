# 로그인·계정 연동 설계

레오파드 모프 계산기의 인증 설계 문서입니다. 소셜 로그인을 추가하거나 계정 관련 코드를 고칠 때
**먼저 이 문서를 읽고**, 바꾼 내용을 여기에도 반영해 주세요.

- 최초 작성 2026-07-27
- 대상 provider: 이메일+비밀번호(구현됨), Google(구현됨), Kakao(예정), Apple(iOS 출시 시 필수)
- 백엔드: Supabase Auth

> **문서 상태 표기**
> `[구현]` 코드에 반영됨 · `[설계]` 결정됐으나 미구현 · `[확인필요]` 사실 확인이 끝나지 않음

---

## 1. 무엇을 풀어야 하는가

소셜 로그인을 여러 개 붙이면 "한 사람 = 한 계정"을 유지하기가 어려워집니다. 문제는 네 갈래입니다.

1. **중복 계정** — 같은 사람이 구글로도, 카카오로도, 이메일로도 가입해 계정이 셋으로 쪼개짐
2. **계정 탈취** — 이메일만 같으면 자동으로 합쳐 주는 순진한 구현은 남의 계정을 뺏는 통로가 됨
3. **이메일 없는 가입** — 카카오는 이메일이 선택 동의라 이메일을 아예 못 받을 수 있음
4. **로그인 수단 상실** — 마지막 남은 로그인 수단을 해제하면 본인도 못 들어옴

여기에 **Apple App Store 심사 지침 4.8**이 겹칩니다. iOS 앱에서 구글·카카오 로그인을 제공하면
동등한 대체 로그인 수단을 같이 제공해야 합니다.

---

## 2. 위협 모델 — 이메일 자동 연동은 왜 위험한가

가장 중요한 부분입니다. **"이메일이 같으면 같은 사람"이라는 가정은 성립하지 않습니다.**

### 2.1 선점형 계정 탈취 (account pre-hijacking)

공격자가 **피해자보다 먼저** 피해자의 이메일로 계정을 만들어 두는 방식입니다.

```
1. 공격자가 victim@gmail.com 으로 이메일+비밀번호 가입 (메일 인증은 안 함)
2. 시간이 지나 진짜 주인이 구글 로그인으로 victim@gmail.com 접속
3. 시스템이 "이메일 같네" 하고 자동 연동
4. → 공격자가 예전에 설정한 비밀번호가 여전히 살아 있음
5. → 공격자가 피해자 계정에 그대로 로그인 가능
```

피해자는 정상적으로 자기 구글 계정으로 로그인했을 뿐이라 **이상을 눈치채지 못합니다.**

### 2.2 미검증 이메일을 주는 provider

일부 provider는 사용자가 입력한 이메일을 검증 없이 그대로 넘겨줍니다.
공격자가 자기 소셜 계정의 이메일을 `victim@gmail.com`으로 바꿔 두면, 자동 연동 시 그대로 남의 계정에 들어갑니다.

### 2.3 결론 — 연동 규칙

> **이메일은 "같은 사람인 것 같다"는 힌트일 뿐, 증명이 아니다.**
> 연동은 반드시 **양쪽 모두 검증된 이메일**이거나, **기존 계정에 대한 소유 증명**이 있을 때만 한다.

## 3. 로그인 시 판정 규칙 `[설계]`

소셜 로그인 콜백이 돌아왔을 때 아래 순서로 판정합니다.

| # | 상황 | 처리 |
|---|---|---|
| 1 | 이 provider UID가 이미 연결돼 있음 | 그냥 로그인 |
| 2 | provider가 이메일을 안 줌 | **이메일 수집 화면** → OTP 인증 → 3번으로 |
| 3 | provider 이메일이 **미검증** | 자동 연동 금지. OTP로 직접 인증받고 4번으로 |
| 4 | 검증된 이메일, 같은 이메일 계정 **없음** | 새 계정 생성 |
| 5 | 검증된 이메일, 같은 이메일 계정 **있음** + 그 계정 이메일도 검증됨 | **연동 확인 화면** → 소유 증명 → 연동 |
| 6 | 검증된 이메일, 같은 이메일 계정 있음 + 그 계정 이메일이 **미검증** | **연동 금지.** 기존 계정 인증 먼저 요구 |

### 3.1 "소유 증명"으로 인정하는 것

5번에서 요구하는 증명입니다. 아래 중 **하나**를 통과해야 연동합니다.

- 기존 계정의 **비밀번호 입력** (비밀번호가 설정된 계정인 경우)
- 기존 계정 이메일로 보낸 **일회용 코드(OTP) 입력**
- 이미 연결된 **다른 소셜 로그인**으로 로그인

증명 없이는 절대 합치지 않습니다. 증명을 못 하면 "이미 가입된 이메일입니다.
기존 방법으로 로그인해 주세요"로 안내하고 **새 계정을 만들지도 않습니다.**
(새 계정을 만들어 주면 중복 계정이 늘고, 사용자는 자기 데이터가 사라진 줄 압니다.)

### 3.2 이메일 존재 여부를 알려 주면 안 된다

"이 이메일은 이미 가입돼 있습니다"를 **가입 전에** 알려 주는 API를 만들면
공격자가 이메일 목록을 넣어 가입자를 골라낼 수 있습니다(계정 열거, enumeration).
파충류 커뮤니티처럼 좁은 집단에서는 "누가 이 서비스를 쓰는가" 자체가 사생활입니다.

따라서 **이메일 존재 여부를 조회하는 RPC는 만들지 않습니다.**
중복 판정은 반드시 서버 안에서(OAuth 콜백 처리 중에) 하고, 그 결과로만 화면을 분기합니다.
소셜 로그인 흐름에서는 이미 그 이메일의 소유자가 인증을 마친 상태이므로 알려 줘도 됩니다.

### 3.3 Supabase의 자동 연동 — 끌 수 없습니다 `[확인됨]`

조사 결과 **Supabase는 같은 이메일이면 자동으로 연동하며, 이를 끄는 공식 설정이 없습니다.**
따라서 "자동 연동을 끈다"는 전제로 설계하면 안 됩니다.

다행히 Supabase도 이 공격을 알고 방어를 넣어 두었습니다. 소스(`internal/models/linking.go`)의
`DetermineAccountLinking`은 **검증된(verified) 이메일만** 기존 계정 탐색에 사용합니다.

```go
if email.Verified || config.Mailer.Autoconfirm {
    verifiedEmails = append(verifiedEmails, strings.ToLower(email.Email))
}
```

### 🔴 3.4 그런데 이 방어를 무력화하는 설정이 있습니다

위 코드의 `|| config.Mailer.Autoconfirm` 을 보세요.
**"Confirm email" 설정이 꺼져 있으면 미검증 이메일도 verified로 취급됩니다.**
즉 2장의 선점형 탈취 공격이 그대로 성립합니다.

> **운영 중 반드시 확인** — Supabase → Authentication → Providers → Email →
> **"Confirm email"이 켜져 있어야 합니다.**
> 테스트 편의로 끄고 그대로 배포하면 계정 탈취가 가능한 상태가 됩니다.

(`구글로그인_설정가이드.md`에 이 경고를 반영해 두었습니다.)

### 3.5 그래도 남는 구멍 — 카카오 미검증 이메일 `[테스트 필요]`

카카오는 `is_email_verified: false` 인 이메일을 내려줄 수 있습니다.
**이 값을 Supabase가 verified로 볼지 unverified로 볼지는 조사로 확인하지 못했습니다.**
카카오를 붙이기 전에 **반드시 직접 테스트해서 확인**해야 합니다. verified로 취급된다면
자동 연동 방어가 뚫리므로, 그때는 카카오를 Supabase 기본 흐름에 그대로 태우면 안 됩니다.

## 4. 이메일을 못 받는 경우 `[설계]`

카카오는 이메일이 **선택 동의** 항목입니다. 사용자가 거부하면 이메일 없이 인증이 끝납니다.
전화번호로만 만든 카카오 계정은 이메일 자체가 없을 수도 있습니다. `[확인필요]`

### 처리 원칙

1. **가입을 완료시키지 않습니다.** 이메일 없이 계정을 만들면 나중에 계정 복구·중복 판정·공지 발송이 전부 막힙니다.
2. 인증 직후 **이메일 입력 화면**을 띄웁니다. ("계정 보호를 위해 이메일이 필요해요")
3. 입력받은 이메일로 **OTP를 보내 검증**합니다. 사용자가 타이핑한 이메일은 그 자체로는 신뢰하지 않습니다.
4. 검증이 끝나면 3장의 판정 규칙 4번/5번으로 들어갑니다.
5. 이메일 입력을 거부하면 가입을 취소하고, 왜 필요한지 안내합니다.

> **왜 이렇게까지 하나** — 사용자가 남의 이메일을 입력할 수 있기 때문입니다.
> OTP 검증 없이 그 이메일로 기존 계정을 찾아 연동하면 2장의 공격이 그대로 재현됩니다.

## 5. 로그인 수단 관리 `[설계]`

### 5.1 마지막 수단 해제 금지

**해제 후에도 "사용 가능한 로그인 수단"이 1개 이상 남아야 합니다.**

"사용 가능"의 정의가 중요합니다. 단순히 identity 개수를 세면 안 됩니다.

- 이메일 identity가 있어도 **비밀번호가 설정돼 있지 않으면** 로그인 수단이 아닙니다
  (구글로만 가입한 계정은 이메일 identity가 있어도 비밀번호가 없습니다)
- 따라서 판정은 `소셜 identity 개수 + (비밀번호 설정됨 ? 1 : 0) >= 2` 일 때만 해제 허용

해제하려는 것이 마지막 수단이면 버튼을 비활성화하고 이유를 보여 줍니다.
"이 계정의 유일한 로그인 방법이에요. 다른 방법을 먼저 추가해 주세요."

### 5.2 연동·해제는 민감 작업

- 연동/해제 전에 **재인증**을 요구합니다 (최근 로그인 시각이 오래됐으면 다시 로그인)
- 새 로그인 수단이 추가되면 **기존 이메일로 알림을 보냅니다.**
  탈취당했을 때 본인이 가장 빨리 알아챌 수 있는 신호입니다.

## 6. 탈퇴 시 처리 `[일부 구현]`

현재 `delete_my_account()`는 DB 데이터와 `auth.users`만 지웁니다.
**소셜 provider 쪽 연결은 정리하지 않고 있습니다.** 이건 고쳐야 합니다.

### 6.1 provider별로 해야 할 일

| Provider | 필요한 처리 | 안 하면 생기는 문제 | 상태 |
|---|---|---|---|
| Kakao | 연결 끊기(unlink) API 호출 | 카카오 계정에 앱이 계속 연결된 채로 남음 | `[설계]` |
| Apple | 토큰 폐기(revoke) API 호출 | **App Store 심사 거부 사유** | `[설계]` |
| Google | 토큰 폐기 (권장) | 동의 화면에 앱이 남음 | `[설계]` |

정확한 API 스펙은 조사 결과 반영 후 확정합니다. `[확인필요]`

### 6.2 순서

provider 연결 해제를 **DB 삭제보다 먼저** 시도합니다.
DB를 먼저 지우면 provider 토큰을 잃어버려 연결 해제를 영영 못 합니다.

```
1. 각 provider 연결 해제 시도 (실패해도 기록만 남기고 진행)
2. 개체·페어링·클러치·사진 삭제
3. 동의 기록 익명화 보관 (법정 5년)
4. 프로필 삭제
5. auth.users 삭제
```

연결 해제에 실패한 provider는 별도 테이블에 남겨 두고 재시도할 수 있게 합니다.
(사용자를 붙잡아 둘 수는 없으므로 탈퇴 자체는 진행합니다.)

## 6.5 이미 갈라진 계정을 합치기 `[설계]`

3장의 판정 규칙은 **중복 계정이 새로 생기는 것을 막는** 장치입니다.
하지만 규칙을 넣기 전에 이미 갈라진 계정, 또는 사용자가 일부러 따로 만든 계정은 남습니다.

### 왜 클라이언트에서 못 하나

Supabase의 `linkIdentity`는 **현재 로그인한 사용자에게 새 identity를 붙이는** 기능입니다.
그 identity가 이미 다른 계정에 붙어 있으면 실패합니다. 즉 "계정 A와 계정 B를 합친다"는
identity를 옮기고 + 데이터를 옮기고 + 빈 계정을 지우는 작업이라, `auth` 스키마를 건드릴
권한이 필요합니다. 클라이언트 키로는 불가능하고 `SECURITY DEFINER` 함수가 필요합니다.

### 병합 정책

| 대상 | 처리 |
|---|---|
| 개체·페어링·클러치 | 양쪽 다 유지 (`device` 값을 남길 계정으로 변경). 삭제하지 않음 |
| 프리미엄 코드 | 만료일이 더 늦은 쪽을 살림. 무기한이 있으면 무기한 우선 |
| 프로필(이름·닉네임·전화) | 비어 있지 않은 값 우선. 둘 다 있으면 **남길 계정** 값 유지 |
| 동의 기록 | 더 최근 동의 시각 채택. 선택 동의는 **둘 중 하나라도 동의면 동의**로 보지 않고, 남길 계정 기준 |
| 로그인 수단 | 양쪽 identity 를 모두 남길 계정으로 이동 |

> 선택 동의(마케팅)를 "하나라도 동의면 동의"로 처리하지 않는 이유 —
> 동의하지 않은 계정의 사용자에게 광고를 보내는 결과가 될 수 있어 법적 위험이 있습니다.

### 실행 조건

병합은 되돌릴 수 없으므로 **양쪽 계정 모두에 대한 소유 증명**을 요구합니다.
한쪽만 증명된 상태로 합치면 그게 곧 계정 탈취입니다.

### 현 시점 결론

서비스 초기라 중복 계정 수가 적습니다. **자동 병합 UI는 만들지 않고**,
3장의 예방 규칙을 먼저 넣은 뒤 병합은 **관리자 수동 도구**로 처리합니다.
사용자에게는 "기존 방법으로 로그인해 주세요" 안내와 문의 창구를 제공합니다.

## 7. Apple App Store 심사 지침 4.8 `[확인됨]`

### 7.1 조항 요약 (2026-06-08 개정판)

소셜 로그인으로 **주 계정을 만들거나 인증하는** 앱은, 아래 3요건을 갖춘
**동등한 대체 로그인**을 함께 제공해야 합니다.

1. 수집 데이터를 **이름과 이메일로 제한**
2. 계정 생성 과정에서 **이메일을 비공개로 유지할 수 있어야 함**
3. 동의 없이 광고 목적으로 앱 내 상호작용을 수집하지 않음

2019년에는 "Sign in with Apple을 제공하라"였으나 2024년 1월 "위 요건을 갖춘 다른 로그인 서비스"로
문구가 완화됐습니다. **다만 실질은 거의 그대로입니다** — 아래를 보세요.

### 7.2 결론 — 카카오를 넣으면 Sign in with Apple도 넣어야 합니다

| 구성 | 4.8 적용 | 판정 |
|---|---|---|
| 자체 이메일+비밀번호 **만** | **면제** | 면제 조항 1번 "exclusively uses your company's own account systems". 확실함 |
| 카카오/구글 + 자체 이메일+비밀번호 | 적용 | **위험.** 통과 사례 확인 실패, 리젝 사례 다수 |
| 카카오/구글 + Sign in with Apple | 적용 | **안전.** 3요건 충족이 확인된 유일한 서비스 |

**핵심은 2번 요건입니다.** "이메일을 비공개로 유지"하려면 이메일 릴레이 기능이 있어야 합니다.
가입 시 이메일을 직접 받는 자체 계정은 구조적으로 이 요건을 만족할 수 없습니다.
**같은 이유로 구글 로그인도 4.8을 충족하지 못합니다** (이메일 가리기 기능 없음).

Apple 개발자 포럼에서 "이메일+비밀번호 대안을 제공했는데도 리젝"된 사례가 여럿 확인되며,
**성공 사례는 하나도 확인되지 않았습니다.**

> **선택지는 둘 중 하나입니다.**
> (A) 소셜 로그인을 아예 안 넣고 자체 계정만 → 4.8 자체가 적용 안 됨
> (B) 카카오를 넣는다면 Sign in with Apple을 반드시 함께

버튼 배치도 요건입니다 — Apple 버튼을 카카오 버튼보다 **작게 만들거나 스크롤해야 보이게 두면 안 됩니다.**

### 🔴 7.3 한국 개발자 필수 — S2S 알림 엔드포인트 (2026-01-01 시행, 이미 발효)

> "Starting January 1, 2026, developers **based in the Republic of Korea** must provide a
> server-to-server notification endpoint when registering a new Services ID, or updating an
> existing Services ID, to associate their website with an app using Sign in with Apple."

**한국 소재 개발자는 직접 대상입니다.** 엔드포인트가 없으면 Services ID 등록·수정 자체가 막힙니다.
Sign in with Apple을 웹에서 쓰려면 Services ID가 필요하므로 **사실상 선행 조건**입니다.

- HTTPS + **TLS 1.2 이상** 필수, Primary App ID에 등록 (앱 그룹당 1개)
- Apple이 서명된 JWT를 POST → `https://appleid.apple.com/auth/keys` 공개키로 서명 검증 필수

| 이벤트 | 처리 |
|---|---|
| `consent-revoked` | 사용자가 연결 해제 → **세션·토큰 무효화, 로그아웃** |
| `account-delete` | Apple 계정 영구 삭제 → 계정 데이터 처리 |
| `email-disabled` | 릴레이 전달 중단 → **해당 주소로 발송 중지** |
| `email-enabled` | 전달 재개 |

**멱등 처리 필수** — `account-delete`가 중복 전송되는 사례가 보고되어 있습니다.

정적 호스팅(GitHub Pages)에는 이 엔드포인트를 둘 수 없습니다.
**Supabase Edge Function 등 서버 실행 환경이 필요합니다.**

### 7.4 함께 걸리는 조항 — 5.1.1(v)

앱 내 **회원탈퇴 기능이 필수**이고, **소셜 연결 해제 수단도 앱 안에** 있어야 합니다 (2022-06-30 시행).
Sign in with Apple 사용 시 탈퇴 처리에서 **`/auth/revoke` 호출이 필수**이며,
계정 비활성화만으로는 불충분하다고 Apple이 명시합니다.

→ 6장의 탈퇴 처리 설계가 이 조항을 만족시키기 위한 것입니다.

## 9. 빠뜨리기 쉬운 것들

설계·구현 시 함께 챙겨야 하는 항목입니다.

### 인증 관련
- **Apple은 최초 1회만 이름·이메일을 준다** — 첫 콜백에서 저장 안 하면 영영 못 받음 `[확인필요]`
- **Apple Private Relay 이메일** — `@privaterelay.appleid.com` 형태. 이메일 기준 중복 판정이 무의미해지고,
  사용자가 전달을 끊으면 메일이 반송됨 `[확인필요]`
- **소셜 쪽 이메일이 바뀌는 경우** — provider UID를 기준으로 삼고 이메일은 참고값으로만 씀
- **provider 장애** — 카카오 점검 중이면 로그인 불가. 다른 수단 안내 문구 필요
- **로그아웃 범위** — 카카오는 "앱 로그아웃"과 "카카오계정 로그아웃"이 다름. 공용 PC 고려

### 계정 병합 시
- **두 계정에 각각 데이터가 있으면?** — 개체·페어링·클러치를 어느 쪽으로 합칠지 정책 필요.
  현재 `claim_device`는 기기→계정 이관만 처리하고 계정↔계정 병합은 없음
- **프리미엄 코드 승계** — 양쪽에 코드가 있으면 만료일이 더 긴 쪽을 살릴지 등
- **병합은 되돌릴 수 없음** — 실행 전 확인 화면 필요

### 법적·정책
- **소셜 가입자도 만 14세 이상 확인**이 필요 (현재 동의 게이트가 처리 중)
- **개인정보처리방침에 provider별 수집 항목 명시** — 카카오·애플 추가 시 방침도 같이 고쳐야 함
- **카카오 비즈앱 전환** — 이메일 수집 동의항목을 쓰려면 필요할 수 있음 `[확인필요]`
- **탈퇴 후 재가입** — 같은 소셜 계정으로 다시 가입해도 이전 데이터는 없음을 명확히 안내
  (현재 탈퇴 화면에 이미 문구 있음)
