# 결제와 이용 권한 기반

- 기준: `supabase_v49.sql`
- 현재 상태: 2026-08-04 라이브 DB 적용 및 권한 검증 완료
- 실결제 상태: 미연결
- 상품 상태: 활성 상품 없음
- 서버 상태: 결제 상태 조회와 이니시스 테스트 요청 생성기 준비, 결제 시작은 강제 차단

## 목표

이니시스·카카오 등 결제사를 바꾸더라도 케어로그와 프리미엄 권한 로직을 다시 만들지 않도록
상품, 가격, 주문, 결제, 환불, 구독, 이용 권한을 결제사 어댑터와 분리합니다.

상품명과 설명은 `ko`, `en`, `zh`, `ja` 키를 담는 JSON으로 저장해 I18n을 유지합니다.
금액은 소수점 오차가 없는 최소 화폐 단위 정수로 저장합니다.

## 데이터 경계

| 영역 | 역할 | 브라우저 권한 |
|---|---|---|
| 상품·가격 | 판매 항목과 서버 기준 금액 | 활성 항목 조회만 |
| 주문 | 사용자 요청과 금액 스냅샷 | 본인 조회만 |
| 결제·환불·구독 | PG사 처리 결과 | 본인 조회만 |
| 이용 권한 | 프리미엄 기능 활성 기간 | 본인 조회만 |
| 웹훅 이벤트 | 서명 확인, 중복·재시도 상태 | 접근 불가 |

브라우저는 가격, 결제 완료 상태, 권한 기간을 직접 쓰지 못합니다. 주문 생성 함수는 활성 가격을
DB에서 다시 읽고, 결제 승인 함수는 주문의 금액과 통화를 PG사 결과와 비교합니다.

## 서버 어댑터 순서

1. PG사의 원본 요청 본문과 서명 헤더를 서버에서 검증합니다.
2. 검증된 이벤트 ID와 본문 해시만 `billing_claim_webhook`에 전달합니다.
3. 이미 처리 중인 이벤트는 건너뛰고, 중단된 처리는 5분 뒤 다시 가져올 수 있습니다.
4. 승인 결과는 `billing_capture_order`에 전달합니다.
5. 주문 금액·통화·상태가 모두 일치할 때만 결제와 이용 권한을 한 트랜잭션으로 기록합니다.
6. 실패하면 `billing_finish_webhook`으로 실패 상태를 남겨 안전하게 재시도합니다.

웹훅 원문과 카드·계좌 정보는 DB에 저장하지 않습니다. PG사 비밀키와 서비스 역할 키도 브라우저
코드나 정적 파일에 두지 않고 서버 환경 변수에서만 사용합니다.

## 프리미엄 코드 통합

기존 프리미엄 코드를 사용하면 `premium_code` 출처의 이용 권한이 함께 만들어집니다. 기존에 이미
사용된 코드도 v49 적용 시 이용 권한으로 옮겨집니다. 화면에서 호출하는 `premium_status` 형식은
유지하므로 기존 계산기와 케어로그의 프리미엄 판정은 바뀌지 않습니다.

## 적용과 다음 단계

운영 DB에는 전체 설치 파일이 아니라 `supabase_v49.sql`만 적용했습니다. 실제 결제를 열지 않은
상태에서 기존 프리미엄 코드와 이용 권한 연결, 본인 권한 조회, 공개 QR 사진 접근을 확인했습니다.

Cloudflare Worker에는 `/api/billing/status`를 추가했습니다. 한국어·영어·중국어·일본어로 현재
판매가 닫혀 있음을 알리고, `/api/billing/*`의 다른 요청은 가맹점 승인 전까지 `503`으로 차단합니다.
이니시스 테스트 요청 생성기는 주문 상태·KRW 통화·서버 금액을 확인한 뒤 공식 서명 필드를 만들며,
비밀 서명키와 서버 모듈은 정적 배포 파일에 포함하지 않습니다. 현재 화면에는 결제 버튼을 연결하지
않았고 실결제 승인·취소·환불·웹훅 처리도 열지 않았습니다.

가맹점 계약과 테스트 상점 정보가 발급되면 서버 주문 생성과 승인·취소·환불 어댑터를 연결하고
아래를 검증합니다.

- 같은 결제 알림이 여러 번 와도 결제와 권한이 한 번만 생성되는지
- 브라우저가 보낸 금액을 바꿔도 서버 주문 금액으로 거절되는지
- 승인 실패, 시간 초과, 취소, 전액·부분 환불이 정확히 반영되는지
- 계정 탈퇴 뒤 결제 보존 기록과 활성 이용 권한이 분리되는지
- 한국어·영어·중국어·일본어 결제 안내와 오류 문구가 같은 의미인지

사업자 표시, 통신판매 관련 정보, 최종 이용약관·개인정보처리방침·환불 정책을 채우기 전에는
실제 판매를 활성화하지 않습니다.
