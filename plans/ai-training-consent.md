# 사진 AI 학습 동의 — 결정 사항과 남은 것

- 작성일: 2026-08-09
- 상태: **범위 결정됨 · 약관 초안 미작성 (#11)**
- 관련: `terms.html`, `plans/transfer-docs-roadmap.md`

## 왜 지금 정해야 하는가

가입이 아직 막혀 있습니다. 즉 지금 올라와 있는 사진은 사실상 운영자 본인 것뿐이고,
**소급 동의 문제가 없는 유일한 시점**입니다. 가입을 연 뒤에 넣으면 그 시점 이후
회원 전원에게 다시 동의를 받아야 하고, 그건 실무적으로 거의 불가능합니다.

## 결정된 것 (2026-08-09)

| 항목 | 결정 |
| --- | --- |
| 학습 대상 | **개체 사진과 등록하는 사진만.** 브리더 로고·프로필 이미지는 제외 |
| 판매 계획 | **없음** |
| 모델 공개 | **없음.** 서비스 내부 전용 |
| 용도 | 학습 후, **브리딩 시 예상 해칭 개체를 이미지 예시로 보여 주는 기능** |

이 조합이면 약관이 단순해집니다. 제3자 제공도, 외부 판매도 없으므로 '서비스 제공
목적 내 이용' 에 가깝게 쓸 수 있습니다. 다만 **수집 목적(개체 기록)과는 다른
목적**이므로 별도 동의는 여전히 필요합니다.

## 약관·동의에 반드시 들어가야 하는 것

### 1. 별도 선택 동의로 받는다

약관 문장 추가로는 부족합니다. 가입 시 **선택 동의 체크박스**를 따로 두고,
**끄고도 가입이 되어야** 합니다. 필수로 묶으면 동의 자체가 무효가 될 수 있습니다.

### 2. 내 사진이 남의 화면에 영향을 준다는 점

이게 가장 놓치기 쉬운 부분입니다. A 의 사진으로 학습한 모델이 B 의 교배 예시를
그리면, **A 개체의 생김새가 B 의 화면에 나타납니다.** 동의 문구에 이걸 밝히지
않으면 나중에 분쟁의 핵심이 됩니다. "내 사진이 다른 회원의 예시 이미지 생성에
쓰일 수 있다" 를 명시해야 합니다.

### 3. 철회의 한계를 정직하게

동의를 철회하면 **이후 학습에서는** 제외할 수 있지만, 이미 학습이 끝난 모델에서
특정 사진의 기여만 제거하는 것은 **기술적으로 불가능**합니다.

- 쓰면 안 되는 문장: "삭제하면 모델에서도 지워집니다"
- 쓸 수 있는 문장: "철회 이후의 학습분부터 제외되며, 기존 모델은 다음 재학습
  시점에 반영됩니다"

지킬 수 없는 약속을 적으면 그 문장이 그대로 책임이 됩니다.

### 4. 생성 이미지는 예측이 아니라 그림이다

계산기는 확률을 말하지만 생성 이미지는 확률을 말하지 않습니다. "이렇게 나온다" 로
읽히면 분쟁이 됩니다. 약관보다 **화면 표기**의 문제이기도 합니다 — 생성된 이미지
옆에 '예시이며 실제 부화 개체와 다릅니다' 를 붙여야 합니다.

### 5. 사진에 딸려 오는 개인정보

- **EXIF 위치정보** — 확인 결과 **이미 제거되고 있습니다.** `assets/imgtool.js` 가
  올리기 전에 canvas 로 다시 그립니다(`drawImage` → `toBlob`). canvas 를 거치면
  EXIF 는 남지 않으므로 GPS 좌표도 함께 사라집니다. 회전 정보만 `createImageBitmap`
  이 픽셀에 반영해 줍니다. 따로 손댈 것이 없습니다.
- **배경의 사람** — 학습 대상에서 거르는 기준이 필요합니다.

## 비공개 개체 사진 — 결정됨 (2026-08-09)

**동의한 회원의 사진은 공개 여부와 무관하게 학습에 씁니다.** 동의 문구에 그 사실을
그대로 적습니다 — '공개하지 않은 개체의 사진도 포함됩니다' 를 빼면 안 됩니다.

공개한 것만 쓰면 학습 데이터가 크게 줄고, '공개하면 학습에 쓰인다' 는 규칙은 공개
자체를 꺼리게 만듭니다.

## 이미지 검수 — 가입 오픈 전에 필요합니다 (2026-08-09)

사진은 아무거나 올라올 수 있고 지금은 아무도 보지 않습니다. 회원이 늘면 약관에
어긋나는 이미지(성인물·도박 등)가 반드시 올라옵니다. 두 가지가 동시에 걸립니다.

- **서비스 문제** — 공개 개체 카드와 분양 갤러리에 그대로 실립니다.
- **학습 문제** — 검수 안 된 이미지가 학습에 들어가면 모델이 오염되고, 그 뒤에
  빼내는 것은 불가능합니다. 학습 전에 거르는 것 말고는 방법이 없습니다.

그래서 **가입 오픈을 막는 항목**으로 올립니다. 회원이 없을 때는 안 터지지만, 회원을
늘리는 것이 목표이므로 늘기 전에 있어야 합니다.

### 필요한 것 (v68 + 관리자 화면)

| | |
| --- | --- |
| 목록 | 회원 전체의 개체 사진을 최근순으로. 개체·소유자·올린 시각 |
| 미리보기 | `animal-photos` 는 비공개 버킷이라 서명 주소로 |
| 삭제 | 사진만 지우기 / 개체를 비공개로 돌리기 두 단계 |
| 학습 제외 | 지우지는 않되 학습에서만 빼는 표시 — 애매한 것에 씁니다 |
| 처리 기록 | 누가 언제 무엇을 왜 지웠는지. 분쟁이 나면 이것만 남습니다 |

기존 `admin_member_actions` 와 같은 자리에 붙입니다. 사진 경로 규칙은
`a/u_<소유자uuid>_<파일명>` 입니다(supabase_v25.sql).

### 약관에 함께 들어갈 것

- 올릴 수 있는 이미지의 기준과, 어긋나면 **사전 통보 없이 삭제**할 수 있다는 것
- 삭제 사유와 이의 제기 방법
- 반복 위반 시 이용 제한

## 관리자 열람 범위 — 사진만이 아니라 개체 페이지까지 (2026-08-09)

QR 로 넘어가는 개체 페이지에 무엇이 실려 있는지 우리가 모릅니다. 실시간 검수도,
에이전트로 훑는 것도 한계가 있으므로 관리자가 직접 볼 수 있어야 합니다.

### 다만 두 가지를 갈라야 합니다

**이미 공개된 것과 아닌 것.** `is_public` 이 켜진 개체는 토큰만 있으면 누구나
봅니다. 관리자가 그걸 보는 것은 추가 침해가 아니라 당연한 검수입니다. 반면
비공개 개체를 상시 열람하는 것은 성격이 다릅니다.

| 대상 | 열람 | 조건 |
| --- | --- | --- |
| 공개 개체 (`is_public` · `is_listed`) | 상시 | 이미 남에게 보이는 것 |
| 비공개 개체 | 신고 접수 시 · 학습 전 검수 시 | **열람 기록을 남긴다** |

**가리기와 고치기.** 필요한 것은 '가리기' 입니다.

- 필요함 — 사진 삭제, 개체 비공개 전환, 학습 제외, 이용 제한
- 위험함 — 이름·모프·기록을 관리자가 임의로 바꾸는 것

회원의 기록을 관리자가 고칠 수 있으면 그건 더 이상 회원의 기록이 아닙니다.
잘못된 내용은 회원에게 고치게 하고, 우리는 보이지 않게 하는 데까지만 갑니다.
(예외: 종·성별처럼 자식 혈통과 어긋나 회원 스스로 못 고치는 경우 —
supabase_v63.sql 의 잠금과 같은 자리입니다.)

### 열람 기록이 왜 필수인가

관리자가 남의 사육 기록과 사진을 볼 수 있게 되는 순간, 그 권한을 **누가 언제
무엇에 썼는지** 가 남아야 합니다. 없으면 남용을 막을 방법도, 남용하지 않았음을
보일 방법도 없습니다. 분쟁이 나면 이 기록만 남습니다.

### 약관·처리방침에 반드시

'관리자가 회원의 개체 기록과 사진을 열람·삭제·비공개 처리할 수 있다' 를 적지
않으면 몰래 보는 것이 됩니다. 열람 사유(신고 처리·학습 전 검수)와 범위도 함께
적습니다.

## 조치했으면 알린다 (2026-08-09)

관리자가 사진을 지우거나 개체를 비공개로 돌렸으면, 회원이 관리 페이지에 들어왔을
때 **왜 그렇게 됐는지** 가 배너로 보여야 합니다. 안 알리면 회원에게 남는 것은
'내 사진이 왜 사라졌지' 뿐이고, 그 질문은 우리에게 오지 않고 다른 데로 갑니다.

### 설계에서 걸리는 것 넷

**① 안내는 대상보다 오래 살아야 합니다.**
사진을 지웠는데 안내를 그 사진에 매달아 두면 같이 사라집니다. 개체(또는 회원)에
독립적으로 답니다 — `animal_documents` 에 FK 를 안 건 것과 같은 이유입니다.
개체까지 지운 경우에는 회원 단위로 남아야 합니다.

**② 기록과 안내는 다른 것입니다.**

| | 성격 | 지울 수 있나 |
| --- | --- | --- |
| 처리 기록 (관리자용) | append-only. 분쟁 나면 이것만 남습니다 | 아니오 |
| 안내 (회원용) | 읽고 닫을 수 있어야 합니다 | 닫기만, 기록은 남음 |

같은 사건의 두 얼굴입니다. 회원이 닫았다고 기록까지 지우면 안 됩니다.

**③ 어디에 띄우는가.**
개체 관리 페이지 상단만으로는 부족합니다. 100마리를 키우는 사람은 **어느 개체가
조치됐는지 모릅니다.** 케어 개체 목록의 그 카드에도 표시가 있어야 찾아갑니다.

**④ 이의 제기 경로를 함께.**
안내만 하고 답할 곳이 없으면 항의가 다른 경로로 갑니다. 안내 배너 안에 문의
수단을 같이 둡니다.

### 사유는 분류 + 자유 입력

관리자가 문장을 직접 쓰되, 분류를 함께 고릅니다(성인물·도박·저작권·개체와 무관한
사진·기타). 분류가 있어야 통계가 되고, 다른 관리자가 같은 사안을 다르게 처리하는
것을 줄일 수 있습니다.

### 약관에 들어갈 문장

- 약관에 어긋나는 이미지는 **사전 통보 없이** 삭제하거나 비공개로 돌릴 수 있음
- 다만 조치 후 **사유를 회원에게 알림**
- 이의 제기 방법과 처리 기간
- 반복 위반 시 이용 제한

성인물 같은 것은 사전 통보를 기다릴 수 없습니다. '사전 통보 없이 조치하고 사후에
알린다' 가 실제로 지킬 수 있는 순서입니다.

## 학습 전 거르기

동의를 받았다고 전부 학습에 넣지 않습니다. 순서는 이렇습니다.

1. 회원 동의 (`agree_ai_train` + `ai_train_version`)
2. 관리자 검수를 통과했거나 아직 신고되지 않은 것
3. 학습 제외 표시가 없는 것

세 번째가 없으면 '지우기는 과하지만 학습에는 넣기 싫은' 이미지를 다룰 방법이
없어집니다.

## 개인정보처리방침에 함께 들어갈 것

AI 와 별개지만 같은 회차에 정리해야 하는 것입니다.

**탈퇴 후 남는 서류·거래 이력.** 계정 삭제는 `public.animals` 만 지웁니다.
`animal_documents` 와 `animal_transfers` 는 FK 가 없어 그대로 남습니다(그게 설계
의도입니다 — 지울 수 있는 장부는 장부가 아닙니다). 그런데 서류에는 **상대방 이름·
주소·허가번호**가 들어 있습니다. 보관 기간과 익명화 방식을 정해야 합니다.
