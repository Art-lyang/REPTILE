# 사진 AI 학습 동의 — 결정 사항과 남은 것

- 작성일: 2026-08-09
- 상태: **범위 결정됨 · 약관 초안 미작성 (#11)**
- 관련: `terms.html`, `plans/transfer-docs-roadmap.md`

## 왜 지금 정해야 하는가

가입이 아직 막혀 있습니다. 즉 지금 올라와 있는 사진은 사실상 운영자 본인 것뿐이고,
**소급 동의 문제가 없는 유일한 시점**입니다. 가입을 연 뒤에 넣으면 그 시점 이후
회원 전원에게 다시 동의를 받아야 하고, 그건 실무적으로 거의 불가능합니다.

## 결정된 것 (2026-08-09)

| 항목 | 결정 |
| --- | --- |
| 학습 대상 | **개체 사진과 등록하는 사진만.** 브리더 로고·프로필 이미지는 제외 |
| 판매 계획 | **없음** |
| 모델 공개 | **없음.** 서비스 내부 전용 |
| 용도 | 학습 후, **브리딩 시 예상 해칭 개체를 이미지 예시로 보여 주는 기능** |

이 조합이면 약관이 단순해집니다. 제3자 제공도, 외부 판매도 없으므로 '서비스 제공
목적 내 이용' 에 가깝게 쓸 수 있습니다. 다만 **수집 목적(개체 기록)과는 다른
목적**이므로 별도 동의는 여전히 필요합니다.

## 약관·동의에 반드시 들어가야 하는 것

### 1. 별도 선택 동의로 받는다

약관 문장 추가로는 부족합니다. 가입 시 **선택 동의 체크박스**를 따로 두고,
**끄고도 가입이 되어야** 합니다. 필수로 묶으면 동의 자체가 무효가 될 수 있습니다.

### 2. 내 사진이 남의 화면에 영향을 준다는 점

이게 가장 놓치기 쉬운 부분입니다. A 의 사진으로 학습한 모델이 B 의 교배 예시를
그리면, **A 개체의 생김새가 B 의 화면에 나타납니다.** 동의 문구에 이걸 밝히지
않으면 나중에 분쟁의 핵심이 됩니다. "내 사진이 다른 회원의 예시 이미지 생성에
쓰일 수 있다" 를 명시해야 합니다.

### 3. 철회의 한계를 정직하게

동의를 철회하면 **이후 학습에서는** 제외할 수 있지만, 이미 학습이 끝난 모델에서
특정 사진의 기여만 제거하는 것은 **기술적으로 불가능**합니다.

- 쓰면 안 되는 문장: "삭제하면 모델에서도 지워집니다"
- 쓸 수 있는 문장: "철회 이후의 학습분부터 제외되며, 기존 모델은 다음 재학습
  시점에 반영됩니다"

지킬 수 없는 약속을 적으면 그 문장이 그대로 책임이 됩니다.

### 4. 생성 이미지는 예측이 아니라 그림이다

계산기는 확률을 말하지만 생성 이미지는 확률을 말하지 않습니다. "이렇게 나온다" 로
읽히면 분쟁이 됩니다. 약관보다 **화면 표기**의 문제이기도 합니다 — 생성된 이미지
옆에 '예시이며 실제 부화 개체와 다릅니다' 를 붙여야 합니다.

### 5. 사진에 딸려 오는 개인정보

- **EXIF 위치정보** — 확인 결과 **이미 제거되고 있습니다.** `assets/imgtool.js` 가
  올리기 전에 canvas 로 다시 그립니다(`drawImage` → `toBlob`). canvas 를 거치면
  EXIF 는 남지 않으므로 GPS 좌표도 함께 사라집니다. 회전 정보만 `createImageBitmap`
  이 픽셀에 반영해 줍니다. 따로 손댈 것이 없습니다.
- **배경의 사람** — 학습 대상에서 거르는 기준이 필요합니다.

## 비공개 개체 사진 — 결정됨 (2026-08-09)

**동의한 회원의 사진은 공개 여부와 무관하게 학습에 씁니다.** 동의 문구에 그 사실을
그대로 적습니다 — '공개하지 않은 개체의 사진도 포함됩니다' 를 빼면 안 됩니다.

공개한 것만 쓰면 학습 데이터가 크게 줄고, '공개하면 학습에 쓰인다' 는 규칙은 공개
자체를 꺼리게 만듭니다.

## 이미지 검수 — 가입 오픈 전에 필요합니다 (2026-08-09)

사진은 아무거나 올라올 수 있고 지금은 아무도 보지 않습니다. 회원이 늘면 약관에
어긋나는 이미지(성인물·도박 등)가 반드시 올라옵니다. 두 가지가 동시에 걸립니다.

- **서비스 문제** — 공개 개체 카드와 분양 갤러리에 그대로 실립니다.
- **학습 문제** — 검수 안 된 이미지가 학습에 들어가면 모델이 오염되고, 그 뒤에
  빼내는 것은 불가능합니다. 학습 전에 거르는 것 말고는 방법이 없습니다.

그래서 **가입 오픈을 막는 항목**으로 올립니다. 회원이 없을 때는 안 터지지만, 회원을
늘리는 것이 목표이므로 늘기 전에 있어야 합니다.

### 필요한 것 (v68 + 관리자 화면)

| | |
| --- | --- |
| 목록 | 회원 전체의 개체 사진을 최근순으로. 개체·소유자·올린 시각 |
| 미리보기 | `animal-photos` 는 비공개 버킷이라 서명 주소로 |
| 삭제 | 사진만 지우기 / 개체를 비공개로 돌리기 두 단계 |
| 학습 제외 | 지우지는 않되 학습에서만 빼는 표시 — 애매한 것에 씁니다 |
| 처리 기록 | 누가 언제 무엇을 왜 지웠는지. 분쟁이 나면 이것만 남습니다 |

기존 `admin_member_actions` 와 같은 자리에 붙입니다. 사진 경로 규칙은
`a/u_<소유자uuid>_<파일명>` 입니다(supabase_v25.sql).

### 약관에 함께 들어갈 것

- 올릴 수 있는 이미지의 기준과, 어긋나면 **사전 통보 없이 삭제**할 수 있다는 것
- 삭제 사유와 이의 제기 방법
- 반복 위반 시 이용 제한

## 관리자 열람 범위 — 사진만이 아니라 개체 페이지까지 (2026-08-09)

QR 로 넘어가는 개체 페이지에 무엇이 실려 있는지 우리가 모릅니다. 실시간 검수도,
에이전트로 훑는 것도 한계가 있으므로 관리자가 직접 볼 수 있어야 합니다.

### 다만 두 가지를 갈라야 합니다

**이미 공개된 것과 아닌 것.** `is_public` 이 켜진 개체는 토큰만 있으면 누구나
봅니다. 관리자가 그걸 보는 것은 추가 침해가 아니라 당연한 검수입니다. 반면
비공개 개체를 상시 열람하는 것은 성격이 다릅니다.

| 대상 | 열람 | 조건 |
| --- | --- | --- |
| 공개 개체 (`is_public` · `is_listed`) | 상시 | 이미 남에게 보이는 것 |
| 비공개 개체 | 신고 접수 시 · 학습 전 검수 시 | **열람 기록을 남긴다** |

**가리기와 고치기.** 필요한 것은 '가리기' 입니다.

- 필요함 — 사진 삭제, 개체 비공개 전환, 학습 제외, 이용 제한
- 위험함 — 이름·모프·기록을 관리자가 임의로 바꾸는 것

회원의 기록을 관리자가 고칠 수 있으면 그건 더 이상 회원의 기록이 아닙니다.
잘못된 내용은 회원에게 고치게 하고, 우리는 보이지 않게 하는 데까지만 갑니다.
(예외: 종·성별처럼 자식 혈통과 어긋나 회원 스스로 못 고치는 경우 —
supabase_v63.sql 의 잠금과 같은 자리입니다.)

### 열람 기록이 왜 필수인가

관리자가 남의 사육 기록과 사진을 볼 수 있게 되는 순간, 그 권한을 **누가 언제
무엇에 썼는지** 가 남아야 합니다. 없으면 남용을 막을 방법도, 남용하지 않았음을
보일 방법도 없습니다. 분쟁이 나면 이 기록만 남습니다.

### 약관·처리방침에 반드시

'관리자가 회원의 개체 기록과 사진을 열람·삭제·비공개 처리할 수 있다' 를 적지
않으면 몰래 보는 것이 됩니다. 열람 사유(신고 처리·학습 전 검수)와 범위도 함께
적습니다.

## 조치했으면 알린다 (2026-08-09)

관리자가 사진을 지우거나 개체를 비공개로 돌렸으면, 회원이 관리 페이지에 들어왔을
때 **왜 그렇게 됐는지** 가 배너로 보여야 합니다. 안 알리면 회원에게 남는 것은
'내 사진이 왜 사라졌지' 뿐이고, 그 질문은 우리에게 오지 않고 다른 데로 갑니다.

### 설계에서 걸리는 것 넷

**① 안내는 대상보다 오래 살아야 합니다.**
사진을 지웠는데 안내를 그 사진에 매달아 두면 같이 사라집니다. 개체(또는 회원)에
독립적으로 답니다 — `animal_documents` 에 FK 를 안 건 것과 같은 이유입니다.
개체까지 지운 경우에는 회원 단위로 남아야 합니다.

**② 기록과 안내는 다른 것입니다.**

| | 성격 | 지울 수 있나 |
| --- | --- | --- |
| 처리 기록 (관리자용) | append-only. 분쟁 나면 이것만 남습니다 | 아니오 |
| 안내 (회원용) | 읽고 닫을 수 있어야 합니다 | 닫기만, 기록은 남음 |

같은 사건의 두 얼굴입니다. 회원이 닫았다고 기록까지 지우면 안 됩니다.

**③ 어디에 띄우는가.**
개체 관리 페이지 상단만으로는 부족합니다. 100마리를 키우는 사람은 **어느 개체가
조치됐는지 모릅니다.** 케어 개체 목록의 그 카드에도 표시가 있어야 찾아갑니다.

**④ 이의 제기 경로를 함께.**
안내만 하고 답할 곳이 없으면 항의가 다른 경로로 갑니다. 안내 배너 안에 문의
수단을 같이 둡니다.

### 사유는 분류 + 자유 입력

관리자가 문장을 직접 쓰되, 분류를 함께 고릅니다(성인물·도박·저작권·개체와 무관한
사진·기타). 분류가 있어야 통계가 되고, 다른 관리자가 같은 사안을 다르게 처리하는
것을 줄일 수 있습니다.

### 약관에 들어갈 문장

- 약관에 어긋나는 이미지는 **사전 통보 없이** 삭제하거나 비공개로 돌릴 수 있음
- 다만 조치 후 **사유를 회원에게 알림**
- 이의 제기 방법과 처리 기간
- 반복 위반 시 이용 제한

성인물 같은 것은 사전 통보를 기다릴 수 없습니다. '사전 통보 없이 조치하고 사후에
알린다' 가 실제로 지킬 수 있는 순서입니다.

## 즉시 삭제가 아니라 보류 (2026-08-09)

바로 지우는 대신 **보류 상태**로 돌리고, 기간 안에 회원이 조치하고 우리가 확인하면
풀어 줍니다. 확인이 안 되면 그때 삭제합니다.

### 보류가 무엇인지부터

**보류는 '남에게 안 보이게 하는 것' 이지 '회원에게서 뺏는 것' 이 아닙니다.**

| | 보류 즉시 |
| --- | --- |
| 공개 카드·분양 갤러리·QR | **바로 안 보임** |
| 학습 대상 | **바로 제외** |
| 회원 본인 화면 | **그대로 보임** — 자기 기록입니다 |
| 회원의 교체·삭제 | 됩니다. 오히려 그걸 하라고 두는 상태입니다 |

남에게 보이는 것을 끊는 것은 미룰 이유가 없습니다. 유예가 필요한 쪽은 '지우는 것'
입니다.

### 상태가 도는 길

```
정상 ──(관리자 보류 + 사유)──▶ 보류
                                 │
              회원이 교체·삭제 ──┤──▶ 확인 대기 ──(관리자 확인)──▶ 정상
                                 │
                기간 만료 ───────┴──▶ 삭제
```

'검수 확인이 우리 쪽에서 되지 않으면' 은 **확인 대기까지 갔는데 우리가 안 본
경우** 도 포함합니다. 그때 삭제되면 회원 잘못이 아닌데 자료가 사라집니다.
확인 대기로 넘어오면 **기간을 멈추는** 편이 맞습니다. 안 그러면 우리가 늦은 대가를
회원이 치릅니다.

### 두 갈래로 나눕니다

| 등급 | 무엇 | 조치 |
| --- | --- | --- |
| **중대 위반** | 성인물 · 도박 · 명백한 위법물 · 직접적 피해를 끼칠 수 있는 것 | **즉시 삭제** |
| 일반 위반 | 개체와 무관한 사진 · 저작권 의심 · 판단이 갈리는 것 | 보류 → 기간 만료 시 삭제 |

유예를 두는 이유는 '회원이 고칠 기회' 인데, 중대 위반은 고쳐서 될 성질이 아니고
유예 기간 동안 우리 서버에 두는 것 자체가 문제입니다.

**즉시 삭제라도 조용히 지우지 않습니다.** 사유 안내와 처리 기록은 똑같이 남습니다.
알리지 않는 삭제는 회원 입장에서 '사라짐' 과 구별되지 않습니다.

### 즉시 삭제할 때 사본을 남길 것인가

오판했을 때 되돌릴 방법이 필요합니다. 이의 제기 대비로 **7일** 사본을 보관합니다
— 다만 **아동 성착취물은 사본도 두면 안 됩니다.**
보관 자체가 문제가 되는 부류라 즉시 완전 삭제하고, 필요하면 신고 절차를 따릅니다.

즉, 즉시 삭제 안에서도 한 번 더 갈립니다.

| | 사본 보관 |
| --- | --- |
| 성인물 · 도박 · 피해 유발 | 이의 제기용으로 **7일** 보관 |
| 아동 성착취물 등 | **보관 없이 완전 삭제** |

### 기간은 하나가 아니라 둘입니다 (2026-08-09)

섞으면 안 되는 두 시계가 있습니다.

| | 무엇 | 제안 |
| --- | --- | --- |
| **회원의 대응 기간** | 보류 통보 → 교체·삭제·이의 제기 | **7일** |
| **우리의 확인 기간** | 확인 대기 → 복구 또는 삭제 | **7일 이내** |
| **즉시 삭제 사본 보관** | 오판 대비 이의 제기용 | **7일** |

'아무리 길어도 7일' 은 **우리 쪽 처리**에 두는 것이 맞습니다. 회원에게 약속하는
응답 속도이고, 지키기도 우리 손에 달렸습니다.

### 왜 7일인가 — 3일도 30일도 아닌

**3일은 회원이 알아차리기 전에 끝납니다.** 지금 안내는 관리 페이지 배너뿐이라,
매일 들어오는 사람이 아니면 못 봅니다. '몰라서 못 한' 삭제가 대부분이 되고 그게
그대로 항의로 돌아옵니다.

**30일은 운영 규모에 안 맞습니다.** 1인 운영에서 한 달치 대기 목록을 들고 가는
것은 부담입니다.

⚠️ 다만 이건 짚어 둡니다 — **기간을 늘려도 관리자 작업량은 늘지 않습니다.**
보류 항목은 자동 만료되어 삭제되므로 매일 볼 필요가 없고, 쌓이는 것은 목록의
길이일 뿐입니다. 실제 작업은 판단 두 번(보류를 걸 때, 이의 제기가 왔을 때)이고,
**기간이 짧을수록 이의 제기가 늘어 두 번째 판단이 많아집니다.**

7일은 그 사이의 절충입니다. 메일 알림이 붙으면 그대로 두어도 되고, 배너뿐인
동안 '몰라서 놓친' 건이 눈에 띄게 많으면 그때 늘리면 됩니다.

### 참고 — 3일로 두면 생기는 일

**회원이 알아차려야 시작됩니다.** 지금 안내는 관리 페이지 배너뿐입니다. 매일
들어오는 사람이 아니면 3일 안에 볼 수 없고, 그러면 '몰라서 못 한' 삭제가 대부분이
됩니다. 그게 그대로 항의로 돌아옵니다.

**짧게 둬서 얻는 것이 없습니다.** 보류에 들어간 순간 공개도 학습도 이미 끊겼습니다
— 남에게 보이지 않고 모델에도 안 들어갑니다. 유예 기간에 남아 있는 위험이 없습니다.
유예는 '지우기 전 대기' 일 뿐이므로, 짧게 잡으면 회원 자료만 억울하게 사라집니다.

**메일을 보낼 수단이 아직 없습니다.** 별도 발송 연동이 없어 Supabase Auth 메일
말고는 경로가 없습니다. 메일 알림이 붙으면 7일도 무리가 아니지만, 배너뿐인 상태로
3일은 사실상 '3일 안에 로그인한 사람만' 입니다.

### 시계를 멈추는 규칙

- 회원이 교체·삭제하거나 이의를 제기하면 → **확인 대기**, 회원 시계 정지
- 우리가 확인하면 → 복구 또는 삭제, 사유 안내
- 우리가 7일 안에 확인하지 못하면 → **회원에게 유리하게**, 즉 삭제하지 않고
  대기 유지. 우리가 늦은 대가를 회원이 치르지 않게 합니다

### 중대 위반은 이 기간과 무관합니다

성인물·도박·직접적 피해는 즉시 삭제이므로 대응 기간이 없습니다. 이의 제기는
삭제 뒤에 받고, 그래서 사본을 짧게 보관합니다.

`supabase_v?.sql` 에 이미 `public.purge_expired` 와 pg_cron 설정이 있습니다
(`consent_archive` 를 `purge_after` 로 지웁니다). 같은 자리에 붙이면 됩니다 —
**새 장치를 만들 필요가 없습니다.**

⚠️ 다만 그 파일 주석에 'pg_cron 이 없으면 함수만 만들어진다' 고 되어 있습니다.
**pg_cron 이 실제로 켜져 있는지 확인해야 합니다.** 안 켜져 있으면 보류가 영원히
보류로 남습니다 — 자동 삭제를 약관에 적어 놓고 실제로는 안 도는 상태가 가장

### 약관 문장

- 약관에 어긋나는 이미지는 **사전 통보 없이 비공개(보류) 처리**할 수 있음
- 조치 후 사유를 알리고, **{N}일 안에** 교체·삭제하지 않으면 삭제됨
- **성인물·도박 등 중대 위반과 직접적 피해를 끼칠 수 있는 이미지는 즉시 삭제**
  (이 경우에도 사유는 알립니다)
- 회원이 조치하면 확인 후 복구하며, 확인이 지연되는 동안 기간은 멈춤
- 명백히 위법한 콘텐츠는 **즉시 삭제**
- 이의 제기 방법과 처리 기간
- 반복 위반 시 이용 제한

N = **7일** 로 정했습니다(2026-08-09).

## 목적을 어떻게 적는가 (2026-08-09)

### 관리자 열람 — 데이터 수집이 아니라 우리 페이지를 지키는 것

운영자 설명: 음란물이 올라와 QR·링크로 돌고 크롤러가 주워 가면, **그게 걸린 곳이
우리 스튜디오 페이지**입니다. 회원 데이터를 보고 싶어서가 아니라 우리 도메인에서
나가는 것을 책임져야 해서입니다.

이 프레이밍이 약관 문구를 바꿉니다. 목적을 어떻게 적느냐가 정당성을 정합니다.

| 문구 | 성격 |
| --- | --- |
| '관리자가 회원의 개체 기록과 사진을 열람할 수 있다' | 넓고 방어하기 어려움 |
| '서비스에서 공개되는 페이지에 실린 이미지를 검수하기 위해 열람한다' | 좁고 정당함 |

같은 기능인데 후자가 훨씬 튼튼합니다. **목적·범위·보존기간을 좁게 적을수록 강해
집니다.** 그리고 이건 실제 이유와도 맞습니다.

약관에는 이렇게 갑니다.

- 열람 목적 — **공개 페이지·분양 갤러리·QR 로 노출되는 이미지의 검수**
- 범위 — 공개된 것은 상시, 비공개는 신고 접수 시에 한함
- 기록 — 비공개 열람은 사유와 함께 남김
- 한계 — **가리기까지. 내용을 임의로 고치지 않음**
- 규모가 커지면 자동 검수 등 다른 수단으로 대체 (양날의 검이라는 인식을 명시)

### AI 학습 — 지금은 좁게 두고, 준비되면 다시 받는다

LoRA 는 아직 시작도 준비도 안 된 상태입니다. 그러면 **지금 세부 목적을 적을 수
없습니다.** 모르는 것을 넓게 적어 두면 두 가지가 다 나빠집니다 — 넓은 동의는
무효 위험이 커지고, 실제로 만들 때 목적이 달라져 어차피 재동의를 받게 됩니다.

앞서 '가입 오픈 전이 유일하게 깨끗한 시점' 이라고 적었는데, 그건 **목적을 정확히
아는 경우** 에 한합니다. 지금은 그렇지 않습니다.

그래서 이렇게 갑니다.

1. `agree_ai_train` 은 v14 부터 이미 있고 약관에도 조항이 있습니다. **그대로 둡니다.**
2. 문구는 **지금 실제로 하는 것까지만** 좁게 적습니다. LoRA·해칭 예상 이미지 같은
   구체적 용도는 **적지 않습니다.**
3. 실제로 준비되면 그때 `ai_train` 을 v2 로 올리고 다시 묻습니다.
   `admin_consent_stale()` 이 대상을 뽑아 줍니다 — v67 이 정확히 이걸 위한 것입니다.

즉 **가입 오픈이 AI 학습 동의에 발목 잡히지 않습니다.** 오픈은 예정대로 가고,
학습은 준비될 때 별도로 받습니다.

## 학습 전 거르기

동의를 받았다고 전부 학습에 넣지 않습니다. 순서는 이렇습니다.

1. 회원 동의 (`agree_ai_train` + `ai_train_version`)
2. 관리자 검수를 통과했거나 아직 신고되지 않은 것
3. 학습 제외 표시가 없는 것

세 번째가 없으면 '지우기는 과하지만 학습에는 넣기 싫은' 이미지를 다룰 방법이
없어집니다.
