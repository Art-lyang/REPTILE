## 먼저 읽으세요 — 양도·거래 기록 표를 만들려는 분께

혈통서와 CITES는 별개입니다. 혈통서는 조율할 것이 없으니 그대로 진행하세요.
**딱 하나 겹치는 것이 '양도 이벤트' 입니다.** 거래 기록을 담는 표가 두 벌
생기면, 한쪽은 CITES 잠금이 걸려 있고 다른 쪽은 안 걸린 상태가 됩니다.
그러면 잠기지 않은 쪽으로 우회하면 되므로 불법 양도 방지가 그대로 뚫립니다.

표를 만들 때 지켜야 할 세 가지입니다. `tests/animal-transfers-contract.test.js`
가 이걸 검사합니다 — 지금은 잠자고 있다가 그런 표가 생기면 깨어납니다.

1. **개체로 향하는 `on delete cascade` 를 걸지 마세요.**
   `public.save_row` 는 개체를 고칠 때 delete 후 같은 id 로 insert 합니다
   (`supabase_v54.sql`). cascade 를 걸면 개체 이름만 바꿔도 거래 이력이 통째로
   사라집니다. `supabase_v64.sql` 의 `animal_documents` 가 같은 이유로 FK 를
   뺐습니다.

2. **소유권을 옮기기 전에 `public.assert_cites_transferable(animal_id)` 를 부르세요.**
   `supabase_v64.sql` 에 이 목적으로 미리 넣어 둔 함수입니다. 지금 부르는 곳이
   없다고 지우지 마세요. 이걸 안 부르면 '공개는 막혔는데 양도는 되는' 두 번째
   문이 열립니다.

3. **거래 이력은 지울 수 없어야 합니다.** RLS 를 켜고 delete 정책을 두지
   마세요. 지울 수 있으면 추적 장부로서의 가치가 0 입니다.

그리고 표를 만들기 전에 **혈통 스냅샷 문제**를 먼저 결정해야 합니다 (아래 2절).
개체를 넘기면 그 개체를 부모로 쓴 자손의 혈통 표시가 끊깁니다. 결정을 미루고
표부터 만들면, 나중에는 이미 데이터가 깨져 있습니다.

> 선행 조건: `supabase_v64.sql` 이 **아직 적용되지 않았습니다.** 실행 검증이

## 1. 왜 지금 코드를 붙이지 않는가

세 가지가 아직 확인되지 않았습니다. 확인 전에 만들면 전부 다시 만들게 됩니다.

1. **크레스티드게코가 어떤 규제 바구니에 들어가는지.** 크레스티드게코
   (*Correlophus ciliatus*)는 CITES 부속서 종이 아닙니다. 그래서 CITES 서류
   기능을 붙여도 우리 주력 종에는 적용되지 않습니다. 실제 쟁점은 개정
   야생생물법의 **지정관리 야생동물**(사육 허가·신고 화이트리스트) 해당
   여부이고, 이건 고시 목록을 직접 봐야 합니다.
2. **양도·양수 신고 서식과 의무자.** 종별로 신고 의무자(양도인/양수인),
   기한, 제출처가 다릅니다. 서식을 잘못 유도하면 사용자가 과태료를 뭅니다.
3. **전자 접수 창구가 있는지.** 공공 API가 없으면 3단계(국가 연계)는
   출력·안내까지가 한계입니다.

### ⚠️ 설계상 정면충돌: v38이 소유권 변경을 막고 있습니다

`docs/STUDIO.md:315` — `supabase_v38.sql`은 **이미 연결된 부모·페어링 개체의
소유권 변경을 차단**합니다. 좋은 방어이고, 없애면 안 됩니다.

따라서 양도는 `animals.user_id`를 UPDATE 하는 방식으로 만들면 안 됩니다.
대신 이렇게 갑니다.

```
갑이 양도 발의 → transfer 레코드 pending 생성
              → 을이 수락 (별도 계정 또는 초대 링크)
              → SECURITY DEFINER 함수가 원자적으로:
                  ① 혈통·페어링 참조 정리 또는 스냅샷 보존
                  ② animals.user_id 이관
                  ③ transfer.completed_at 기록 (append-only)
```

혈통 처리가 진짜 어려운 부분입니다. 개체를 넘기면 갑의 브리딩 프로젝트에서
그 개체가 사라지는데, **부모로 쓰인 기록까지 사라지면 안 됩니다.** 자손의
혈통 표시가 끊기기 때문입니다. 이관 시 부모 정보를 이름 문자열로 스냅샷
보존하는 설계가 필요합니다. 이건 v31~v38의 소유권 검증을 전부 다시 읽고
결정해야 합니다.

## 3. 3트랙 전략

법적 위험이 낮은 것부터 순서대로 갑니다. 뒤 트랙은 앞 트랙 없이는 못 만듭니다.

### 트랙 A — 민간 계약서 (지금 가능, 위험 낮음)

사육자끼리 쓰는 매매계약서를 만들어 줍니다. 국가와 무관하므로 법적 노출이
거의 없습니다. `docs/transfer-contract-v1.html`이 이 트랙의 산출물입니다.

- 개체 데이터를 자동으로 채워 인쇄·PDF
- 양쪽이 서명한 계약서를 개체에 첨부해 보관
- 개체 이력 QR을 별지로 붙여 "이 개체가 어디서 왔는지"를 증명

**이것만으로도 시장에 없는 기능입니다.** 지금 브리더들은 카톡 대화와
계좌이체 내역이 계약서 전부입니다.

### 트랙 B — 법정 신고서 작성 보조 (법령 확인 후)

신고 대상 종일 때 **서식을 채워서 출력**해 줍니다. 접수는 사용자가 직접
합니다.

- 종을 고르면 "이 종은 신고 대상입니다 / 아닙니다 / 확인이 필요합니다" 안내
- 우리 DB에 있는 값으로 별지 서식 초안 생성
- 필요한 첨부서류 체크리스트와 제출처·기한 안내
- **화면 어디에도 "법적 효력" "대행" "승인"이라는 말을 쓰지 않습니다**

### 트랙 C — 국가 연계와 공인 (장기)

여기서 현실을 짚고 갑니다. **"국가 공인 앱"은 API를 붙인다고 되는 게
아닙니다.** 공공 API는 대개 조회용이고, 신고 접수 API를 민간에 여는 사례는
드뭅니다. 실제 경로는 이쪽에 가깝습니다.

1. 트랙 A·B로 **실사용 데이터와 사용자 수**를 쌓는다.
2. 관계 기관이 못 가진 것을 갖는다 — 개체 단위 혈통·사육 이력·거래 이력.
   국가 시스템은 보통 "누가 몇 마리 갖고 있다"까지고, **개체 하나하나의
   생애**는 없습니다. 이게 우리 협상력입니다.
3. 시범사업·민관협력 공모에 지원하거나, 협회·학회를 통해 제도 논의에
   들어간다.
4. 그 결과로 연계가 열리면 그때 API를 붙인다.

즉 트랙 C의 준비물은 코드가 아니라 **데이터 신뢰성**입니다. 그래서
트랙 A 단계부터 이력을 지울 수 없게(append-only) 만들어야 합니다.
`admin/admin-members.js:122`에서 닉네임 이력을 지우지 않고 기준 시각만
옮긴 것과 같은 원칙입니다.

### Phase 1 — 개체 원장 보강 (스키마)

`animals`에 추가할 컬럼입니다. **전부 nullable + 기본값**으로 넣습니다.
기존 개체 수천 건을 깨면 안 됩니다.

```sql
alter table public.animals
  add column if not exists public_no      text,     -- 영구 공개번호 (share_token 과 별개)
  add column if not exists acquired_on    date,     -- 취득일
  add column if not exists acquired_from  text,     -- 취득처 (브리더명·샵·수입)
  add column if not exists acquire_kind   text,     -- self_bred / purchased / imported / gifted
  add column if not exists marking        text,     -- 마이크로칩·표식
  add column if not exists legal_status   text,     -- none / cites / domestic_regulated / unknown
  add column if not exists legal_ref      text,     -- CITES 등록번호 등
  add column if not exists deceased_on    date,     -- 폐사일
  add column if not exists deceased_note  text;
```

`public_no`가 중요합니다. `share_token`은 사용자가 껐다 켜면 바뀌는 값이라
서류의 개체 식별자로 쓸 수 없습니다. 발급 후 절대 바뀌지 않는 번호가 따로
필요합니다.

| `health.*` | 케어로그에서 끌어오기 가능 | 급이·탈피는 자동, 병력은 입력 |
| `legal.*` | 종 마스터 + 입력 | **Phase 4** |
| `doc.number` | 발급 시 생성 | append-only 일련번호 |

## 6. 하지 말아야 할 것

- **"법적 효력이 있는 계약서" 표기.** 효력은 내용과 당사자가 만드는 것이지
  우리가 보증할 수 있는 게 아닙니다.
- **신고 대행.** 사용자를 대신해 관청에 접수하는 순간 책임 주체가 됩니다.
- **CITES 해당 여부 자동 판정.** 부속서는 개정됩니다. 자동 판정이 틀리면
  사용자가 처벌받습니다. 안내는 하되 판정은 사용자와 관청에 남깁니다.
- **주민등록번호 수집.** 개체 거래에 수집 근거가 없습니다.
- **거래 이력 삭제 기능.** 지우면 추적 체계로서의 가치가 0이 됩니다.
  회원 탈퇴 시에도 개체 원장의 이전 기록은 익명화하되 보존하는 설계를
  검토해야 합니다 (이건 개인정보 보호와 충돌하므로 법률 검토 대상).
